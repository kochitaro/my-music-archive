## ①向け：実装結果

「写真移行・復旧」パネルを追加した。旧領域の整理と、旧版タブによって分岐した新旧両方の退避・復旧を実装。自動統合は行わない。Cover Art ArchiveのURL経路は変更していない。

- 新版・旧v03・旧v1を、それぞれ写真本体入りのversion 3 JSONとして書き出せる。移行保存が容量不足で止まっていても、旧JSONの書き出しとファイルからの読み戻し確認を利用できる。
- 実際に保存したファイルを再選択して読み込み、全記録・全フィールド・添付写真文字列を現在の各保存元と照合する。書き出しボタンを押しただけでは整理・復旧の条件を満たさない。
- 整理は、移行・保存後にページを再読み込みし、保存済みの記録・写真を再取得できた場合に限る。確認ダイアログで表示確認を求め、保存ロック内で再照合して、一致する旧キーだけを削除する。
- 分岐した場合は保存・整理を停止し、新旧のJSONをそれぞれ書き出す。両方の読み戻し確認後、採用するJSONの件数・写真・内容を画面で確認して復旧する。旧領域を保持したまま新版へ確定し、通常の保存を再開できる。

判定：合成データによる自動検証は成功。レビュー対象として提出する。本番採用の判断は①・③レビュー後。

## 利用手順

### 旧データの整理

1. 旧版・別タブの編集を終えて閉じる。移行または保存が成功したら新版を再読み込みし、Listening / Collection / Liveの記録・写真を確認する。
2. 「写真移行・復旧」で新版と、存在する旧領域それぞれのJSONを保存する。既存の通常Export JSONも利用できる。
3. 「保存した新旧JSONを読み戻し確認」で保存したファイルを選ぶ。全保存元に対応するファイルを照合する。内容が完全一致している場合は1ファイルで複数領域の照合を満たせる。確認情報はそのページだけに保持するため、再読み込みしたら再選択する。
4. 「確認済みの旧データを整理」を選び、表示確認に回答する。現在の新版と完全一致した旧領域だけを削除する。一致しない旧領域は保持する。退避JSONは整理後も保管する。

新版を編集して旧記録と一致しなくなった場合は、安全側に倒してその旧キーを残す。部分一致・類似判定での削除は行わない。

### 旧版タブで分岐した場合

1. 未保存の文章があればコピーして保管し、編集タブを閉じる。未保存フォームが残っている間、復旧はその入力を破棄しないよう停止する。必要なら文章を回収して再読み込みする。
2. 新版側の「写真移行・復旧」で新版JSON・旧v03 JSON・存在すれば旧v1 JSONを別名で保存する。新旧どちらの領域も自動上書き・自動削除しない。
3. 各ファイルを読み戻し確認する。「採用する写真付きJSONを選ぶ」で採用する内容を指定し、件数・写真・「記録の内容を確認」の内容を確認する。片方の採用、または利用者が別途用意した統合済みJSONの採用が可能。アプリ内の自動統合はない。
4. 「確認したJSONを採用して復旧」の確認後、新版への復元を確定する。旧領域と両方の退避ファイルは残る。成功したら保存を再開できる。
5. 整理する場合は、改めて再読み込み・ファイルの照合・整理を行う。復旧途中で保存元が変わったら中止し、最新の両方のJSONを再度退避・照合してやり直す。

旧mainは削除されたキーを持つ古い画面のままでは既存の比較保護で保存停止する。旧mainを再読み込みした後は旧キーを新規作成できるので、そのケースも検出・復旧対象にした。

### 新旧が併存する容量がない場合

新方式の参照スナップショットを書けなくても旧キーを先に削除しない。画面に「旧データは保持」「旧JSONを保存・読み戻し確認」「容量に余裕のある別の隔離環境へ復元」を案内する。退避JSONを保管し、容量のある別のブラウザプロファイル／隔離originで復元・再読み込み確認する。同じ環境で容量条件が解消した場合は再読み込みで移行を再試行できる。サイトデータの一括消去は手順に含めない。

## ③向け：保存の境界と中断時の扱い

既存の写真保存 `photo-store.js` に加え、整理・復旧の制御を `photo-lifecycle.js` に分けた。新旧JSONを扱うスキーマ検証と写真のコピー・読み戻し照合は既存の処理を使用する。通常保存、移行、整理、復旧は旧mainと同じWeb Lock `mla:my-music-archive-pilot-v03:write` を共有する。

### 整理

- 再読み込み時に実際に読み出せた新版スナップショットと、整理直前のスナップショットが同じことを要求する。移行・保存が行われた同じページのままでは整理できない。
- 全保存元について、ファイルから読み戻した内容との照合を要求する。照合情報は保存元の生文字列にひも付ける。別タブのstorageイベントで無効にし、処理中にも生文字列の再比較を行う。
- ロック内で現在の新版写真をIndexedDBから読み戻し、旧領域を移行形式へ正規化して全件照合する。未知フィールドも比較対象。一致するキーだけを削除予定にする。
- 削除前に、IndexedDB `mla-photo-maintenance-v1` / store `state` に「対象の新版スナップショット」と「整理後に期待する旧キー値」を書き、トランザクション完了を待つ。その後、非同期処理中に新旧保存元が変わっていないことを再確認してから削除する。
- 整理後、新版スナップショット自体は書き換えない。旧キー削除直後、画面状態の更新前に止まっても、次回起動ではジャーナルの期待値と実際の旧キーを確認して保存を再開できる。
- 2キーの削除途中で止まった場合、期待値と違うキーが残るので保存・整理を停止する。残存領域と新版を退避・読み戻し確認し、明示的な復旧後に整理を再試行する。自動で残りを消すことはない。
- ジャーナル保存に失敗した場合は旧キーを削除しない。旧キーに新たな保存がある場合も、ジャーナルまたは旧領域指紋の不一致で再読み込み後まで分岐を検出する。

### 復旧

保存ロック内で全保存元と読み戻し確認情報を取得し、選択したJSONの写真をコピーして読み戻す。全フィールドを照合した後、保存元と照合情報を再確認する。新版の参照を一度のlocalStorage書き込みで確定するまで、現在の新版・旧データは変更しない。写真書き込み失敗、参照書き込み失敗、保存元更新のいずれも旧参照と旧領域を保持する。

確定時には旧領域の現在の指紋と新しい世代IDを保存する。古い整理ジャーナルが復旧後の新しいスナップショットを誤って停止させないようにする。写真本体は引き続き追記方式で、既存写真・未参照写真のGCは実施しない。

旧v1にentryIdがない場合、新規移行と旧JSON書き出しに同じ決定的IDを使用し、ファイル読み戻しを再現可能にした。すでに8b205c3でランダムIDを生成して移行したv1と旧原本が一致しない場合は旧キーを保持し、採用するJSONの明示的な復旧を使う。

## localStorage使用量

合成PNG 128×128pxを写真として持つ6記録（3種類に各2件）。計測はorigin内の全キーについて `2 × (キー名のUTF-16長 + 値のUTF-16長)` を合計した文字列量。端末のディスク使用量やブラウザのquota課金量を測定したものではない。

| 項目 | 整理前 | 整理後 |
| --- | ---: | ---: |
| 新版キー | 5,020相当bytes | 5,020相当bytes |
| 旧v03キー | 911,246相当bytes | 0 |
| 合計 | 916,266相当bytes | 5,020相当bytes |

削減は911,246相当bytes（約99.45%）。IndexedDBの写真と整理ジャーナルはこの計測に含めていない。同じ画像の繰り返しは写真ストアでは同じIDを利用する。容量不足の確認は実容量を埋めず、書き込みエラーと合成の総文字数上限の注入で行った。

## 残課題と切り戻し

- Safari実機は未確認。前回報告の合成データによる移行・表示・写真付きJSON往復に加え、今回の整理と分岐復旧の操作確認が必要。OSによる強制終了・電源断・自動ストレージ消去は検証していない。中断試験はページ終了、および削除直後の例外注入と再読み込み。
- 排他を保証できる旧版は取得時main `c2c719d` のように同じWeb Lockを利用する版。ロックを無視するさらに古い版・拡張機能等について、localStorageにはタブ横断のCASがなく、最終確認と削除の間の任意書き込みを完全には排除できない。注入試験は更新を受信・確認した状態で中止できることを検証した。整理前に旧タブを閉じる必要があり、任意の旧版との同時編集を保証するものではない。
- 自動統合、写真GC、大量記録の性能最適化、ファイル保存先のOS権限確認、旧JSON自体が破損している場合の専用回収UIは未実装。破損・写真欠落で照合できない領域は無理に整理・復旧しない。複数の新旧JSONを手動で整える際は必ず原本を保管する。
- 整理後に8b205c3へアプリだけ戻すと、新しい整理ジャーナルを認識しないので分岐停止となり得る。切り戻しは先に新旧の写真付きJSONを退避し、容量のある隔離環境の旧mainで採用JSONを復元・照合する。旧領域を削除した後も写真本体・退避JSONは保管し、サイトデータ一括消去を切り戻しに使用しない。
