## 1. 現行検索の構造

`search.js` は画面とSearch Lab共通の通信・検索モジュール。全API要求を直列化し、開始間隔1250ms、各試行タイムアウト20000ms。429/502/503/504、通信障害、本文読み取り失敗を含め最大4試行。再試行待機は2/4/6秒と数値Retry-Afterの大きい方を使用。URL単位の進行中要求共有、5分・最大180件のメモリーキャッシュがある。

アーティスト検索は正規化、ひらがな・カタカナ、artist/alias/sortnameの検索、必要時の前方一致、上位15候補の別名補完を行う。完全一致が複数なら候補選択、一意なら作品を100件ずつ全取得し、MBID重複除去、Album/EP/Single順・発売日順で整列。補完や多数ページ取得は精度を維持するため省けない。

アルバム名検索は直接release-group検索。100件単位の生データoffsetを使い、正規化タイトル一致度と発売日で整列する。画面は30件ずつ表示し、必要になるまで次のAPIページを取らない。

`index.html` は検索世代番号で古い結果を無効化し、検索状態を成功後に確定する。クリア、検索方式変更、Listening/Collection/Live変更で世代番号が進む。

## 2. 測定条件・再現方法

MusicBrainz実ネットワークへの要求は **0件**。実サービスの3〜10秒の原因を直接測定した結果ではない。

1. Node v24.22.1 VMの合成時刻モデル。API応答250ms、成功時JSON解析5msを固定し、間隔待機・再試行待機を仮想時刻に加算。100作品を使用。`wallMs`は実行器の実時間であり、モデルの検索時間とは別物。
2. Python Playwright + Chromium 156、ローカルHTTPサーバー、隔離プロファイル、外部通信をすべて遮断しMusicBrainz応答をroute.fulfillで代替。105作品（2ページ）、日英、320px。旧版・新版それぞれ初回と同条件再検索を各1回。要求間隔は実時間、エラー検証のみPlaywright clockで待機を進める。
3. ブラウザーで検索submit直前から完了status代入まで計測。fetch開始・応答・JSON、同期DOM構築を試験用コードで記録。DOM時間は画像読み込み・合成・描画完了を含まない。計測コードは配信する試験用コピーだけに挿入し製品には追加していない。
4. 重複除去・タイトル整列は別途100行の単独処理を測定。キャッシュ済みアーティスト候補処理も単独測定。これらはend-to-end時間に加算しない。ページのCPU負荷や計時分解能の影響を受ける。
5. ブラウザーのアーティスト初回はアルバム名検索の後に行うため、既存キューの間隔待機も含む。完全独立のcold比較ではない。

## 3. 合成時刻モデルの内訳と改善前後

以下はms。通常ケースの旧版・新版のモデル時間は同一。キャッシュ再検索は追加通信・仮想待機0ms（実際のCPU時間が0という意味ではない）。

| 条件 | 間隔待機 | API応答 | JSON | 再試行待機 | 合計 |
| --- | ---: | ---: | ---: | ---: | ---: |
| アーティスト初回（一意、作品1ページ） | 995 | 500 | 10 | 0 | 1505 |
| アルバム名初回 | 0 | 250 | 5 | 0 | 255 |
| 同一条件再検索（両方式） | 0 | 0 | 0 | 0 | 0 |
| アーティスト候補表示 | 0 | 250 | 5 | 0 | 255 |
| 候補選択後の作品取得（1ページ、空キュー） | 0 | 250 | 5 | 0 | 255 |
| 503→成功 | 0 | 500 | 5 | 2000 | 2505 |
| 503 + Retry-After: 5→成功 | 0 | 500 | 5 | 5000 | 5505 |

検索操作からAPI開始までは、空キューではPromiseスケジューリングのみ、既存要求がある場合はキューと間隔待機になる。ブラウザー証跡の `firstFetchDelayMs` はこれらを含む。`net[].apiMs` はローカルモックとの通信処理、`jsonMs` は本文取得・JSON処理であり、MusicBrainzサーバーの応答時間ではない。キュー待機と間隔待機の実ブラウザー内での完全分離は行っていない。Nodeモデルでは間隔待機と再試行待機を個別に記録した。

## 4. 遅延要因と実施した改善

複数API要求が必要なアーティスト検索、別名補完、多ページ取得ではアクセス間隔が支配的となる。一時エラー時は2/4/6秒の再試行待機やRetry-Afterが加わる。通常検索のDOM構築や整列を変更する根拠は得られなかった。

確認した問題は「間隔待機の直前に検索の有効性を確認するが、待機中に全利用者が古くなった場合もAPIを送ってしまう」こと。待機後・fetch直前にも有効性を再確認する最小修正を実施した。進行中要求を共有する新しい利用者がいる場合は要求を維持する。

| 間隔待機中の破棄→新しい要求の条件 | 旧版 | 新版 |
| --- | ---: | ---: |
| 古い検索の不要API要求 | 1件 | 0件 |
| 古い検索の終了まで（モデルms） | 1250 | 995 |
| 終了後に続けた新しい要求（モデルms） | 1250 | 255 |
| 古い検索の開始から新しい要求完了まで（モデルms） | 2500 | 1250 |

warm要求後に250+5msが経過し、残り995msの間隔待機中に旧検索を破棄する固定条件。JSON証跡のこのケースのAPI・待機内訳とcallsは、後続の回復要求までを含む。一般的な検索の改善率には換算しない。旧版・新版の不要要求差を実行で確認し、単体試験で待機中の破棄・共有先が生存する場合・キュー回復を固定した。

## 5. 改善を見送った部分

要求間隔、再試行、タイムアウト、キャッシュ寿命・件数、候補数、作品数、検索条件、結果順序には変更を加えていない。キャッシュ・重複排除は既に機能している。

実ネットワークのMusicBrainz応答時間は未測定。通常検索が速くなったとは判断しない。処理中のfetchや再試行sleep自体は即座に中止しないため、破棄された要求の応答や再試行待機がキューを占有する場合は残る。共有要求の安全性やRetry-Afterを保つため、今回その制御は変更していない。

## 6. 表示変更

検索開始、候補選択後の作品取得、追加読み込みで「検索中…／Searching…」を表示し、再試行中も維持。画面のsearchContextから再試行の内部情報をstatusへ反映するcallbackを除いた。通信モジュールのonRetry診断通知機能は維持する。

最終失敗は「検索できませんでした。時間をおいて再度お試しください。／Search failed. Please try again later.」。例外本文を画面に連結しない。0件・入力不足の既存動作は維持。成功・候補表示・クリア・方式変更・セクション変更後に検索中表示を残さない。言語切替辞書にも両文言を登録した。

追加登録時のアーティスト情報補完は既存の「アーティスト情報を確認中…／Checking artist metadata…」を維持し、再試行通知による上書きをなくした。補完失敗時の名前手入力・保存前確認の動作は変更していない。HTML配置・CSS・ボタン寸法・色・余白・保存方式に変更なし。
