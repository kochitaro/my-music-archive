# 旧キー整理の見直し：①・③向け報告

2026-11-12 UTC。基準 `92dd60426dfa819d7243b116dbaa23e154e7bd4f`。レビュー用ブランチ `review/indexeddb-import-provenance`。隔離Linux・合成記録／画像・使い捨てChromiumプロファイルのみ使用。mainへの反映・マージ・デプロイなし。

## ①向け：変更と結果

前回は整理時の新版と旧データの全件一致が必要だったため、新版だけで追加・編集した場合にも整理できなかった。今回、移行時に取り込めた旧キーと内容のSHA-256指紋を記録し、通常の追加・編集ではその記録を引き継ぐように変更した。

整理時は、現在の新版全体ではなく、移行時に記録した指紋と現在の旧キーの内容を照合する。旧データが変わっていなければ、新版の追加・編集・写真変更後も整理できる。新版の記録・写真を整理操作で書き換えることはない。

維持した条件：

1. 最新の新版と存在する旧領域について、実際に保存した写真付きJSONファイルを再選択し、読み戻して全フィールド・写真文字列を照合する。
2. 最新の新版保存後に再読み込みし、記録・写真を読み出せていることを確認する。整理時にはそのスナップショットと現在の保存元が同じことを要求する。
3. 保存ロック内で旧キーの指紋を確認し、整理ジャーナル保存後にも新旧すべての生文字列を再照合してから削除する。

旧版でも更新された場合は、従来どおり保存・整理を停止する。新版JSONと旧JSONはそれぞれ退避でき、両方を照合したうえで採用内容を確認して復旧する手順も維持した。自動統合は追加していない。

前回報告の「新版編集後は一致せず旧キーを残す」という制約は、今回の移行元記録を持つデータでは解消した。指紋のない過去データについては後述の制約がある。

## ③向け：記録する内容と保存境界

新版の内部スナップショットに次を保存する。写真本体や旧JSON全体の複製はこの項目には持たない。

```json
{
  "importedLegacy": {
    "version": 1,
    "sources": [
      {
        "key": "my-music-archive-pilot-v03",
        "sha256": "sha256-<旧キーの保存文字列のSHA-256>"
      }
    ]
  }
}
```

- 写真コピー・読み戻し・全記録照合が成功した移行／復元候補と、各旧キーを正規化した内容が完全一致する場合だけ移行元として記録する。同じ内容を持つ複数の旧キーはそれぞれ記録できる。無関係な旧キーを、存在していたという理由だけで移行済み扱いにはしない。
- 旧キーの元の保存文字列をUTF-8化してハッシュ化する。キー名と指紋を対にし、整理時にそのキーの現在の文字列から計算し直した指紋と一致することを確認する。空白や直列化順序だけが変わっても安全側に倒して保持する。
- 移行元記録は、写真照合後に新版スナップショットと同じlocalStorage書き込みで確定する。コピー途中や参照の書き込み失敗で移行済みの記録だけが残ることはない。
- 通常の追加・編集・写真差し替え等では、直前の保存済みスナップショットから移行元記録を引き継ぐ。新版の現在の内容で指紋を更新し直さない。
- JSON読み込みによるアーカイブ全体の置き換え、および分岐復旧では、選択した内容に基づいて移行元記録を作り直す。以前の記録を無条件には引き継がない。変更された旧側を採用しなかった復旧後に、その旧キーを誤って整理することを防ぐ。
- 内部の移行元記録は画面用データと写真付きJSONから取り除く。持ち運びJSONは従来のversion 3形式のまま。JSONから移行元の履歴を無条件に持ち込むことはしない。
- 移行元記録の型・バージョン・キー名・重複・指紋形式を検証する。不正なら削除を止める。削除予定キー、ジャーナル、削除直前の再確認、途中中断後の停止／復旧は92dd604の方式を維持した。

### 指紋のない92dd604以前のデータ

指紋がなければ過去に何を取り込んだかは断定しない。

- 現在の保存済み新版と旧データが完全一致している場合は、最初の編集の**前**に写真を読み戻して一致を確認し、その旧キーを移行元として記録できる。その後の新版だけの追加・編集では記録を保持する。
- すでに新旧の内容が異なっている既存データから、昔の取り込み履歴は推測しない。その旧キーは保持する。新旧を退避し、採用内容を確認して明示的に復旧する既存手順を利用する。
- 指紋がまだないまま整理する場合の従来の全件一致条件も維持した。空の移行元リストが明示的に保存されている場合は、未取り込みとして扱う。

## 合成データによる自動検証

`tests/indexeddb_provenance.py` を追加。実Chromium／IndexedDB／localStorageを使用し、外部HTTPSは遮断。検証用のクロージャアクセスとエラー注入はインターセプトしたHTMLだけに追加した。

| ケース | 結果 |
| --- | --- |
| 移行時の旧キー名・指紋が元文字列のSHA-256と一致 | 成功 |
| 3種類すべてに記録追加・編集・写真変更し、再編集後も同じ移行元記録を保持 | 成功 |
| 最新JSONと旧JSONを照合・再読み込みした後に、取り込み済みの旧キーだけを整理 | 成功。新版は各3件・全フィールド・写真を維持 |
| 取り込んでいない別の旧v1キー | 保持 |
| 新版だけのJSON照合、保存後の再読み込み不足、古い新版JSONの使用 | 整理拒否・旧キー保持 |
| 整理ジャーナル書き込み失敗 | 新旧とも保持し、再試行で整理成功 |
| 新版編集後、実際の旧mainから別の記録・写真を保存 | 保存・整理停止。再読み込み後も検出 |
| その分岐から新旧それぞれの写真付きJSONを保存・読み戻し | 双方の全フィールド・写真文字列が期待値と一致 |
| 新版側を採用して分岐復旧 | 古い取り込み履歴をリセットし、採用しなかった旧側は保持 |
| 組み合わせた旧領域指紋を一致させた合成ケースでも、個別旧キーの内容が移行時と異なる | 整理拒否。個別指紋による防御を確認 |
| 指紋のない旧試作データで、編集前は一致／すでに編集済み | 前者だけ移行元を確認でき整理成功、後者は履歴を捏造せず保持 |

## 残課題・運用前提

Safari実機、OSによる強制終了／電源断、写真GC、大量記録性能は今回も未確認または対象外。同じWeb Lockを利用する旧main `c2c719d` を競合検証に使った。ロックを無視する任意の旧版との同時編集に対する保証範囲は前回報告と同じで、整理前に旧タブを閉じる必要がある。

すでに編集済みで指紋を持たないデータから、確かな過去の移行履歴を自動復元することはできない。JSONでアーカイブ全体を置き換えた後も、取り込み元と照合できない旧領域は保持する。①・③のレビュー後に本番反映を判断する。
