# 添付写真のIndexedDB移行試作：①・③レビュー用

2026-11-12 UTC。対象 `kochitaro/my-music-archive`、取得時main `c2c719dd1bd25583402e0a2db948e168018ce34e`。作業ブランチ `prototype/indexeddb-photos`。隔離Linux環境・新規Chromiumプロファイル・合成画像/記録のみ使用。本番、main、実利用者データへの反映なし。

## ①向け：結果と判断材料

Listening / Collection / Liveの端末添付画像をIndexedDBへコピーし、保存される記録は`photoId`で参照する試作。画面内では読み出した写真を展開し、既存の一覧・詳細・編集表示を利用する。Cover Art ArchiveのURL生成・外部画像取得の経路は変更していない。JSONは従来と同じversion 3、各記録の`photo`に写真本体を埋め込む持ち運び形式を維持。旧JSONの復元、新方式での写真付きJSON出力/復元、取得時mainアプリへの復元まで自動確認する。

新規写真をIndexedDBへ保存できなければ入力と選択ファイルを保持する。利用者が確認ダイアログで選んだ場合のみ、今回選んだ写真を付けずに記録を保存する。既存記録の差し替え時は元の写真を維持する。キャンセルで入力へ戻れる。復元にはこの部分保存を適用しない。

試作レビューには提出可能。本番採用の判断材料として、Safari実機確認、データ分岐時の運用、旧データを廃棄する時期、容量回収を残す。旧領域を維持するため、この試作を入れただけでは旧写真分のlocalStorage使用量は解放されない。

## ③向け：保存境界と復旧

現行mainの調査対象は`index.html`の`migrate`、`commitDB`、`saveDB`、`resizePhoto`、`art`、`openView`、`openEdit`、写真削除、JSON入出力。現行は縮小JPEGのdata URLを記録の`photo`に格納し、アーカイブ全体をlocalStorageへ書く。Web Locksと保存前文字列の比較、保存失敗時の入力保持が既にある。

試作の保存領域：

| 領域 | 用途 |
| --- | --- |
| localStorage `my-music-archive-pilot-v03` / `my-music-archive-pilot-v1` | 旧原本。試作から変更・削除しない |
| localStorage `my-music-archive-photos-v1` | 新しい記録スナップショット、写真ID、旧領域の指紋 |
| IndexedDB `mla-photos-v1` / store `photos` | SHA-256 ID → 写真data URL本体。追記のみ |

保存順序は次のとおり。

1. 旧版mainと同じWeb Lock名を取得し、記録と移行元が読み込み時点から変わっていないことを確認。
2. 画像文字列から決定的IDを作成。未保存なら追記し、書き込みトランザクションの完了を待つ。
3. 別の読み出しトランザクションで文字列を完全一致照合。全記録を写真付きに再展開して、全フィールドを照合。
4. 非同期処理中の新旧領域変更を再確認してから、参照スナップショットをlocalStorageへ一回で確定。成功後のみ画面側の保存済み状態を更新。

中断・容量エラー・参照確定失敗時には旧参照と写真を残す。再試行は同じIDを使い、既存画像は照合して再利用する。写真差し替え、削除、記録削除、復元でも古い写真本体は自動削除しない。確定前にコピーした未参照画像も残る。これは復旧を優先した試作の制約で、GCは別途設計する。

復元は構造検証後に写真をステージングし、全照合成功後に参照を確定する。失敗した復元は既存スナップショットと写真を保持する。写真IDだけの内部形式を持ち運びJSONとして読み込むことは拒否する。書き出しは画面キャッシュではなく、保存済み参照から写真を読み戻してハッシュを確認する。欠落・破損・読み出し失敗時は利用者に通知し、欠けたJSONを出力しない。起動時に写真が読めない場合も空アーカイブとして上書きしない。

### 旧版タブが残っている場合

取得時mainは同じロックを使うため同時保存は排他される。ただし旧タブは新領域を認識しないので、新方式の更新後にも旧領域へ保存できる。試作は旧領域の更新を検出して保存停止し、新旧双方を保持する。旧領域指紋を新スナップショットに残すため、再読み込みで分岐を見逃さない。

分岐を自動統合するUIは未実装。旧タブを閉じる前にその側のJSON、新版からも写真付きJSONを別々に回収し、差分を合成データ環境で確認する。新版の一般的な「再読み込み」案内だけでは旧領域分岐を解消できない。これは本番前のUX課題。旧タブは新領域の内容を見ることができず、旧版に戻しただけでは試作中の更新は現れない。

### 旧版に戻す手順

1. 試作で写真付きJSONを書き出し、ファイルを別の場所に保管する。旧版タブに独立した更新があれば、旧版側でも別名でJSONを保存する。欠落通知が出る場合は切り戻しを進めず、ブラウザ保存領域を残す。
2. 新旧すべての編集タブを閉じる。隔離環境で取得時mainを起動し、試作のJSONをImport JSONで復元する。3種類の件数・主な入力・添付写真を確認し、再出力したJSONとも照合する。自動検証はこの旧mainへの復元を含む。
3. 旧版への復元は旧領域を書き換えるので、再び試作へ戻す場合は保存停止となる。新旧JSONを保管して統合内容を決めた後、隔離環境で新領域を退避・削除して旧領域から移行し直す。本番での手動キー削除はこの試作の運用対象外。
4. JSON、旧領域、新領域、IndexedDBの退避はレビューと確認が終わるまで削除しない。ブラウザの「サイトデータを消去」は切り戻し操作に使用しない。

写真を含む旧形式JSONはlocalStorageの容量制限を再び受ける。旧版への復元が容量不足になった場合も、ファイルと元の保存領域を維持し、十分な容量のある隔離環境で確認する。

## 未確認事項・Safari実機の引き継ぎ

Safari実機は未実施。Linux Chromiumでの成功をSafari実機の結果とみなさない。実容量を埋める試験は行わず、容量不足は書き込みエラー注入で確認した。OSによる強制終了、ストレージの自動退避/消去、数千件規模の性能・メモリ、アクセシビリティの包括検証、既存テスト全件の新保存キーへの追従も未実施。写真は起動時に全件読み出し、保存時に再照合するため大規模データでの最適化が必要。

Safari実機は合成データで次の代表ケースに限定する。

1. 本番と異なるHTTPS originの隔離環境で、旧版にListening / Collection / Live各1件と異なる合成写真を用意して旧JSONを書き出す。iOS/Safariバージョン、件数、JSONサイズを記録する。
2. 試作を同originで開き、移行後の3種類の一覧・詳細・編集写真を確認する。タブを閉じて開き直して再確認する。
3. 写真付きJSONをFilesへ書き出し、別の隔離originへ読み込んで3種類の写真を確認する。再出力JSONの各記録と写真文字列を元ファイルと比較する。

①・③のレビュー後に、本番への反映と残課題の扱いを判断する。この試作はマージ・デプロイしていない。
